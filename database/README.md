# 룸메이드(Roomade) 데이터베이스 정리

팀명: 하프웨이

이 문서는 `database/schema.sql`과 `database/seed.sql`의 내용을 정리한 것이다. 기준 문서는 `roomade_development_design.md`와 팀 회의에서 정한 7개 테이블 구상이다.

## 1. 파일 구성

| 파일 | 설명 |
|---|---|
| `schema.sql` | 데이터베이스와 테이블, 제약, 트리거를 만든다. |
| `seed.sql` | 개발용 샘플 데이터를 넣는다. 실행하면 기존 데이터를 모두 비운다. |
| `README.md` | 이 문서 |

## 2. 실행 방법

환경은 MySQL 8.0.16 이상이다. CHECK 제약을 쓰기 때문이다. 8.0.46에서 검증했다.

```bash
mysql -u <계정> -p --default-character-set=utf8mb4 < database/schema.sql
mysql -u <계정> -p --default-character-set=utf8mb4 < database/seed.sql
```

MySQL Workbench에서는 새 쿼리 탭에 파일을 열고 번개 아이콘으로 실행한다.

- `schema.sql`은 데이터베이스 `roomade`를 만든다. 이미 있으면 테이블이 없는 것만 만든다.
- 테이블 구조를 바꿔 다시 적용하려면 데이터베이스를 지우고 다시 만들어야 한다. 개발 중에만 한다.
- `seed.sql`은 개발·테스트 DB에서만 실행한다. 실제 데이터가 있는 DB에서는 실행하지 않는다.

## 3. 핵심 규칙

1. **한 회원은 한 방에만 가입한다.** 방 회원 테이블의 회원번호가 UNIQUE다. 방을 나가면 행을 삭제하고, 이후 다른 방에 가입할 수 있다.
2. **방장은 방 관리자다.** 권한의 기준은 방 테이블의 방장 컬럼 하나다. 위임은 이 값을 바꾸는 UPDATE 한 번으로 끝난다. 방장은 위임하기 전에는 방을 나가거나 탈퇴할 수 없고, 이는 서버에서 검사한다.
3. **방 정원은 2명에서 10명이다.** 기본값은 10명이다. 가입할 때 트리거가 방 행을 잠그고 인원을 세므로, 동시에 가입해도 정원을 넘지 않는다. 정원이 차면 오류 메시지 `ROOM_FULL`이 나온다.
4. **같은 계정은 몇 개의 기기로 가입해도 한 명이다.** 인원은 기기가 아니라 회원 기준이다.
5. **초대 코드는 사용 횟수 제한이 없다.** 만료 시각, 활성 여부, 재발급으로 관리하고 인원은 방 정원으로 제한한다.
6. **일정은 구분 없이 모두 방 구성원에게 공유된다.**
7. **물품의 소유자는 등록 회원이다.** 소유 구분은 개인과 공용이다.
8. **전화번호와 닉네임은 중복될 수 없다.** 닉네임 중복 확인은 가입 화면에서 이 값을 조회한다.
9. **계좌 정보는 서버가 암호화한 값만 저장한다.** 암호 키는 DB가 아닌 서버 환경변수로 관리한다. 비밀번호는 해시로만 저장한다.

## 4. 테이블 관계

```text
users 1 ─── 1 room_members N ─── 1 rooms
                                    │
        ┌──────────┬──────────┬─────┼──────────┬──────────────┐
        N          N          N     N          N              N
   room_invitations items schedules cleaning_tasks expenses  (rooms.owner → users)
                                        │            │
                                        N            N
                                 cleaning_records expense_shares
```

room_departures는 rooms와 users를 참조하는 기록용 테이블이다.

## 5. 테이블 설명

### users 회원
| 컬럼 | 설명 |
|---|---|
| user_id | 회원번호, PK |
| login_id | 로그인 ID, UNIQUE |
| password_hash | 비밀번호 해시 |
| name, nickname | 이름과 닉네임, 닉네임 UNIQUE |
| phone | 전화번호, UNIQUE |
| account_encrypted | 암호화된 계좌 정보 |
| birth_date, gender | 생년월일, 성별(MALE, FEMALE, OTHER) |

전화번호, 계좌, 생년월일, 성별은 모두 필수다.

### rooms 방
| 컬럼 | 설명 |
|---|---|
| room_id | 방번호, PK |
| room_name | 방 이름 |
| owner_user_id | 방장 회원번호, FK |
| capacity | 정원, 2에서 10 |
| created_at | 생성일 |

방장은 방을 만들 때 같은 트랜잭션에서 방 회원 테이블에도 넣는다.

### room_members 방 회원
방번호, 회원번호, 가입일. 회원번호가 UNIQUE이고, 정원 초과 방지 트리거가 걸려 있다. 역할 컬럼은 없다.

### room_invitations 방 초대 코드
방번호, 코드 해시, 발급자, 만료 시각, 활성 여부. 코드는 SHA-256 해시로 저장하고 UNIQUE로 조회한다. 코드는 서버에서 충분히 긴 난수로 만든다.

### items 창고 물품
| 컬럼 | 설명 |
|---|---|
| room_id, created_by | 방과 등록 회원, 등록 회원이 소유자 |
| name | 물품 이름 |
| category | FOOD 식료품, SUPPLY 생필품 |
| ownership_type | PERSONAL 개인, SHARED 공용 |
| quantity, unit | 수량과 단위, 수량은 0 이상 |
| expiry_date | 유통기한 |
| barcode, storage_location | 바코드, 보관 위치 |
| status | STORED 보관, USED_UP 사용 완료, DISCARDED 폐기 |

### schedules 일정
방번호, 작성 회원, 제목, 시작과 종료 일시. 종료는 시작 이후여야 한다.

### cleaning_tasks 청소 항목
| 컬럼 | 설명 |
|---|---|
| area_name | 청소 항목 |
| assignee_user_id | 담당 회원, 없으면 NULL |
| next_due_date | 지금 예정된 청소 날짜 |
| repeat_type, repeat_interval | NONE, DAILY, WEEKLY, MONTHLY와 간격 |
| is_active | 활성 여부 |

다음 날짜는 완료하거나 미룰 때 서버가 갱신한다. 완료는 반복 주기에 따라 다음 날짜로, 미루기는 미룬 날짜로 바꾼다. 청소 기록 추가와 같은 트랜잭션으로 처리한다.

### cleaning_records 청소 이력
| 컬럼 | 설명 |
|---|---|
| task_id, assignee_user_id | 청소 항목과 해당 회차 담당자 |
| due_date | 예정 날짜 |
| status | SCHEDULED 예정, DONE 완료, POSTPONED 미룸, SKIPPED 건너뜀 |
| completed_at | 완료일 때만 값이 있다. |
| completed_by | 실제로 청소를 완료한 회원. 담당자 대신 다른 사람이 했을 수 있어서 따로 둔다. |
| postponed_to | 미룸일 때만 값이 있고 예정일보다 뒤여야 한다. |
| memo | 사유 메모 |

### expenses 지출 내역
방번호, 결제 회원, 지출 항목, 금액(원, 0보다 큼), 지출 날짜.

### expense_shares 지출 분담
지출번호, 분담 회원, 분담 금액, 정산 완료 여부와 시각. 한 지출에 같은 회원은 한 번만 들어간다. 결제자 본인의 몫도 한 행으로 넣는다. 분담 금액의 합이 지출 금액과 같은지는 서버가 검사한다.

### room_departures 방 퇴장 기록
방번호, 나간 회원, 사유(LEFT 스스로 나감, KICKED 방장이 내보냄), 퇴장 시각. 방을 나가거나 내보내질 때 서버가 남긴다. 나간 사람이 결제하거나 분담한 지출은 방의 기록으로 남기 때문에, 지출 목록에서 그 사람이 나갔는지 추방됐는지를 보여주는 데 쓴다. 같은 사람이 다시 가입할 수 있어서 여러 행이 생길 수 있다.

## 6. 삭제 규칙

- 방을 삭제하면 그 방의 방 회원, 초대 코드, 물품, 일정, 청소, 지출, 분담이 함께 삭제된다.
- 청소 담당 회원이 삭제되면 담당자 칸이 비워진다.
- 방장인 회원, 물품 등록자, 일정 작성자, 지출 결제자와 분담자는 삭제할 수 없다. 탈퇴 방식은 서버 개발 때 정한다. 실제 삭제보다 비활성 처리가 맞을 수 있다.

### 방을 나갈 때 데이터 처리

외래키가 방이 아니라 회원을 가리키기 때문에, 방 회원 행만 지우면 나간 사람의 물품, 일정, 청소 담당, 지출이 방에 그대로 남는다. DB의 연쇄 삭제로는 "그 방에서의 그 사람"을 지정할 수 없어서, **서버가 한 트랜잭션 안에서 정리한 뒤 방 회원 행을 지운다.** 스스로 나갈 때와 방장이 내보낼 때 같은 정리 함수를 쓴다.

| 데이터 | 처리 |
|---|---|
| 개인 물품 | 삭제 |
| 공용 물품 | 스스로 나갈 때는 방장에게 넘기거나 삭제 중에서 나가는 사람이 고른다. 내보낼 때는 항상 방장에게 넘긴다. |
| 일정 | 삭제 |
| 청소 항목의 담당자 | 비운다. 항목은 방 전체의 규칙이라 남긴다. |
| 예정된 청소 회차 | 담당자를 비운다. |
| 청소 완료·미룸·건너뜀 이력 | 그대로 둔다. |
| 지출과 분담 기록 | 그대로 둔다. 방의 정산 기록이다. |
| 퇴장 기록 | room_departures에 LEFT 또는 KICKED로 남긴다. |

정산 규칙은 이렇다.

- **스스로 나갈 때:** 내가 낼 돈이나 받을 돈이 남아 있으면 나갈 수 없다. 단, 상대가 이미 방에 없으면 막지 않는다.
- **방장이 내보낼 때:** 정산이 안 끝났어도 내보낼 수 있다. 지출과 분담 기록은 그대로 남고, 목록에서 추방됨으로 표시된다.
- **나간 사람과 얽힌 금액:** 정산 요약에 계속 보인다. 받을 돈은 결제한 사람이 정산 완료로 정리할 수 있다.

방장이 혼자 남아 나가면 방이 삭제되고, 방의 모든 데이터가 함께 삭제된다.

## 7. 서버 개발 때 처리할 일

| 항목 | 내용 |
|---|---|
| 방 만들기 | 방과 방장의 방 회원 행을 한 트랜잭션으로 넣는다. |
| 방 가입 | 코드 해시로 방을 찾고, 만료와 활성 여부를 확인한다. 이미 가입했는지 먼저 확인한다. 정원이 차면 `ROOM_FULL`을 받아 안내한다. |
| 방장 위임 | 방장 컬럼을 새 방장으로 바꾼다. |
| 방 나가기와 내보내기 | 방장은 위임 전에는 나갈 수 없다. 나가는 사람의 데이터 정리와 방 회원 행 삭제는 한 트랜잭션으로 처리한다. 물품, 일정 등을 만드는 API는 방 행을 공유 잠금으로 확인해서, 나가는 중인 사람의 데이터가 새로 생기지 않게 한다. |
| 청소 완료와 미루기 | 기록 추가와 다음 날짜 갱신을 한 트랜잭션으로 처리한다. |
| 지출 등록 | 분담 금액의 합이 지출 금액과 같은지 검사한다. |
| 계좌 정보 | 서버에서 암호화하고 복호화한다. 암호 키는 환경변수에 둔다. |
| 정원 변경 | 현재 인원보다 작게 줄이는 것은 DB가 막지 않는다. 허용하기로 정했다. |

## 8. 샘플 데이터 구성

| 방 | 구성 |
|---|---|
| 301호, 정원 4 | 하나(방장), 두리, 세나 |
| 302호, 정원 2 | 민준(방장), 다은, 정원이 가득 참 |
| 무소속 | 한솔, 방 가입 테스트용 |

초대 코드 `ROOM301A`는 사용 가능, `OLDCODE1`은 만료, `ROOM302B`는 정원이 찬 방용이다. 비밀번호 해시와 계좌 값은 모두 가짜다.

## 9. 검증 내용

MySQL 8.0.46에서 다음을 확인했다.

- 스키마와 샘플 데이터가 오류 없이 들어가고 샘플 데이터는 반복 실행이 된다.
- 한 방에만 가입, 정원 초과 거절, 같은 계정 중복 가입 거절이 동작한다.
- 전화번호와 닉네임 중복, 음수 수량, 시간 순서가 잘못된 일정이 거절된다.
- 청소 완료·미룸의 필수 값 규칙, 분담 중복과 정산 값 규칙이 동작한다.
- 방 삭제 때 하위 데이터가 함께 삭제된다.
- 정원 트리거의 동시 가입 상황은 서버 통합 테스트에서 확인했다. 정원 3명인 방에 8명이 동시에 가입하면 2명만 들어간다.
